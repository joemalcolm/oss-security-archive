Prosody XMPP server advisory 2026-11-25 (Multiple Vulnerabilities)

Project
:   Prosody XMPP server

URL
:   https://prosody.im/

Date
:   2026-11-25

This advisory details multiple security vulnerabilities discovered in the
Prosody.im XMPP server software. Fixes are available in Prosody 13.0.8.
This advisory covers the Prosody 13.0 series only.

Deployments on the 0.12 series and earlier are not supported since June 2026,
however we will provide a backported patch for the most critical issues for
distribution maintainers. Unless explicitly stated, the issues listed here
have not been checked in Prosody 0.12.x and earlier.

The recommended advice is for all Prosody users to upgrade to 13.0.8
as soon as possible.

Details of each of the vulnerabilities are below, followed by
acknowledgements. The first 16 issues relate to crossing of various security
boundaries, the remaining 5 issues relate to denial-of-service (i.e.
insufficiently restricted consumption of RAM, CPU or disk space).

This advisory can be found online at:

- https://prosody.im/security/advisory_2026_8112eaa9/ (HTML)
- https://prosody.im/security/advisory_2026_8112eaa9.txt (text)


Cross-host confusion in stanza processing
--------------------------------------------------------

Prosody issue
: #2039

CVEs
: Request pending

CWEs
: CWE-940

Affected versions
: All 13.0 versions prior to 13.0.8

Fixed versions
: 13.0.8


**Description**

In a Prosody instance that is configured to serve multiple virtual hosts or
components, Prosody could process incoming data in the context of the wrong
virtual host, potentially leading to unauthorized access of accounts.

**Affected configurations**

Prosody instances with a single virtual host and no components are *not*
affected.

Prosody instances with multiple virtual hosts, where at least one virtual host
permits potentially malicious users (e.g. hosts with in-band registration
enabled) are most vulnerable to this issue and should upgrade immediately.

**Mitigation**

Upgrade to Prosody 13.0.8 as soon as possible. Running every untrusted host on
a separate Prosody instance is a valid mitigation.

**Fixes**

stanza_router was updated to ensure stanzas are always processed within the
correct host context for the connecting session.

Commit: 489e83c42826


Stream reset did not discard all pending data
------------------------------------------------------------

Prosody issues
: #2037

CVEs
: Request pending

CWEs
: CWE-349

Affected versions
: All 13.0 versions prior to 13.0.8

Fixed versions
: 13.0.8

**Description**

Prosody's xmppstream module did not sufficiently clear all state when a stream
reset was triggered. This could lead to it processing untrusted data on a new
stream, including data injected before TLS.

**Affected configurations**

All configurations are affected. Deployments which support starttls (almost
all) are particularly vulnerable, however direct TLS (e.g. as commonly offered
on port 5223) may not entirely mitigate all issues.

**Mitigation**

Upgrade to Prosody 13.0.8 as soon as possible. If an immediate upgrade is not
feasible, consider allowing only direct TLS connections - but this may break
interoperability with some clients/servers.

**Fixes**

xmppstream was updated to fully reset all state after a stream reset.

Invitation reuse
-------------------------------------------------------

Prosody issue
: #2021

CVEs
: Request pending

CWEs
: CWE-837

Affected versions
: All 13.0 versions prior to 13.0.8

Fixed versions
: 13.0.8

**Description**

A single-use invitation remained cached on an unauthenticated session after it
had been used. The same session could submit additional registration requests
with different usernames. Two concurrent sessions that validated the
invitation before either completed registration could produce the same result.

**Affected configurations**

Deployments using mod_invites and mod_invites_register are affected. These
modules are enabled in the default configuration, but the issues are only
relevant when an invitation is generated and sent to a malicious user.

**Mitigation**

Operators who cannot upgrade immediately may disable invitation-based
registration and password resets. If invitations must remain enabled, restrict
them to administrators and issue them for trusted users only.

**Fixes**

Invitations are marked used in memory, registration hooks ignore used
invitations.

Password-protected MUC exposure
-------------------------------------------------------

Prosody issue
: #2023

CVEs
: Request pending

CWEs
: CWE-862

Affected versions
: All 13.0 versions prior to 13.0.8.

Fixed versions
: 13.0.8

**Description**

XEP-0045 describes the ability to set a password on MUCs to allow access only
to entities which provide the password. This feature is rarely used by modern
clients, preferring the more secure "members-only" MUCs instead for private
group chats.

Because Prosody only checked the password restriction at the time a client
tries to join, various other operations which do not require joining the MUC
were found to be unprotected in MUCs which are not members-only and restricted
access by password only.

Two concrete issues have been identified and fixed:

1) A user who was not an occupant and had no affiliation with a room could
request a mediated invitation. In non-members-only rooms, the default role was
sufficient to permit the request, and password-protected rooms would include
the room password in the invitation (as XEP-0045 recommends). However, this
allowed any XMPP entity to obtain the password for a room whose address they
knew.

2) Message archives of password-protected rooms could be queried without
entering the room or proving knowledge of the password. When
muc_log_by_default was enabled (the default for mod_muc_mam), anyone who knew
the room address could read its history.

**Affected configurations**

The invite issue affects MUC components with password-protected,
non-members-only rooms. The archive issue affects rooms with mod_muc_mam and
logging enabled; the default value of muc_log_by_default is true.

**Mitigation**

Operators who cannot upgrade immediately should make password-protected rooms
members-only where possible. Password protected MUCs can be hidden to prevent
discoverability (if the MUC address is not easy to guess). Archive exposure
can be reduced by disabling MUC logging for password-protected rooms or by
switching the MUC to members-only. Disabling mod_muc_mam removes archive query
exposure but also removes the feature.

Despite the fixes, we strongly recommend that anyone using password-protected
MUCs should switch to members-only MUCs instead, and grant access based on the
managed access control list which Prosody already provides. Password
protection is considered a legacy feature with various inherent problems (e.g.
the passwords are exchanged unencrypted), and may be removed in a future
version.

**Fixes**

Mediated invitations are now rejected unless the inviter is an occupant or has
an affiliation that permits inviting. Unaffiliated non-occupants are now
refused archive queries by default. Because this is potentially a breaking
change (some clients may rely on being able to sync history without joining
the MUC) the previous open behaviour can be restored with
muc_mam_allow_unjoined_queries = true, but password-protected rooms remain
restricted.

Commits: ede9f5173192, be3eb8c0290b

**Attribution**

The mediated-invitation password disclosure was identified in an external
security review.


Non-moderators may modify state and cause occupants to be kicked from MUCs
--------------------------------------------------------------------------

Prosody issue
: #2024

CVEs
: Request pending

CWEs
: CWE-862

Affected versions
: All 13.0 versions prior to 13.0.8.

Fixed versions
: 13.0.8

**Description**

Prosody's muc#admin handler processed changes to a live affiliation record
before applying the required authorization check. By supplying an item with an
affiliation, JID and nick, any XMPP entity could cause a reserved-nickname
conflict kick to be executed against an occupant, including an owner, before
the affiliation change was rejected. The handler could also overwrite
affiliation data such as the reserved nickname and reason for existing
affiliations.

**Affected configurations**

All MUCs are affected in versions prior to 13.0.8, where the exposure to
malicious users is obviously greater for public channels.

**Mitigation**

The best mitigation is to upgrade if you host MUCs where untrusted users are
allowed to join.

**Fixes**

Affiliation changes are authorized before reserved-nickname kicks, and
affiliation data is copied before modification.

Commits: 9f1d26ba8176

**Attribution**

The issue was identified in an external security review.

-----------------------------------------------------------

: #2018

CVEs
: Request pending

CWEs
: CWE-178

Affected versions
: All 13.0 versions prior to 13.0.8.

Fixed versions
: 13.0.8

**Description**

When a module uses Prosody's internal HTTP client API to request a remote URL
that contains a https:// scheme that is not entirely lowercase (e.g. 'HTTPS'

**Affected configurations**

All versions that support HTTPS requests prior to 13.0.8 are affected. Prosody

'https://' if using older Prosody versions.

**Fixes**

The match was made case-insensitive.

mod_http_file_share header injection
-------------------------------------------------

Prosody issue
: #2025

CVEs
: Request pending

CWEs
: CWE-113

Affected versions
: All 13.0 versions prior to 13.0.8

Fixed versions
: 13.0.8


**Description**

An authenticated user could supply a Content-Type value containing carriage
return and line feed characters in a slot request. The value was stored with
the upload and emitted verbatim in the HTTP response for later downloads. This
allowed response-header injection, including Set-Cookie and Refresh headers,
and with a double CRLF could terminate the header block and place attacker-
controlled content in the response body on the file-share origin.

**Affected configurations**

All deployments using mod_http_file_share are affected.

**Mitigation**

Operators who cannot upgrade immediately should disable mod_http_file_share or
restrict upload access to trusted users.

**Fixes**

Slot requests now validate Content-Type against the RFC 6838 media type
syntax.

Insufficient validation of archive query limits
----------------------------------------------------------

Prosody issue
: #2028

CVEs
: Request pending

CWEs
: CWE-1284

Affected versions
: All 13.0 versions prior to 13.0.8

Fixed versions
: 13.0.8

**Description**

Result Set Management (RSM) fields used by message archive queries were parsed
with an overly permissive number conversion. In particular, a negative max
value could become a negative SQL LIMIT, which SQLite treats as unlimited. A
user able to query an archive could therefore bypass max_archive_query_results
and cause the server to materialise an entire archive before discarding the
excess results.

**Affected configurations**

The issue affects mod_mam and mod_muc_mam with SQL storage and archives larger
than max_archive_query_results (default 50).

**Mitigation**

The best mitigation is to upgrade to 13.0.8 or later.

**Fixes**

RSM integer fields are now validated as non-negative xs:int values, invalid
fields result in a bad-request error response, and storage backends have been
updated to reject an invalid limit.

Commits:

7736c449c89a (util.stanza), b4bdfcf99936 (util.rsm), 87112f85540a (mod_mam),
24760c378cb7 (mod_muc_mam), 293d65d0e4ee (mod_storage_sql), 8529a3611c31
(mod_storage_memory).

**Attribution**

This issue was identified in an external security review.


Server-to-Server Policy Bypass
-------------------------------------------------------

Prosody issue
: #2029

CVEs
: Request pending

CWEs
: CWE-862

Affected versions
: All 13.0 versions prior to 13.0.8

Fixed versions
: 13.0.8
**Description**

Prosody checked whether server-to-server communication was enabled only for
the host named in the stream header. After a remote server authenticated to a
permitted host, it could deliver stanzas to another local virtual host on the
same stream even when that second host had mod_s2s disabled with
modules_disabled = {"s2s"}.

**Affected configurations**

Multi-host deployments that disable s2s for only some virtual hosts or
components are affected. A single-host deployment that disables s2s everywhere

**Mitigation**

Operators who cannot upgrade immediately should avoid relying on per-host
mod_s2s disablement for security boundaries. If a host must not accept
server-to-server traffic, isolate it on a separate Prosody instance or use a
module such as mod_firewall to reject traffic.

**Fixes**

Stanzas and dialback results addressed to a host without mod_s2s now close the
stream with policy-violation. Commits: 33d9a7d2cbc4 (mod_dialback),
ff9472b07769 (stanza_router).

The issue was identified in an external security review.


mod_auth_ldap does not reject empty password
----------------------------------------------------------------

Prosody issue
: #2030

CVEs
: Request pending

CWEs
: CWE-303

Affected versions
: All 13.0 versions prior to 13.0.8

Fixed versions
: 13.0.8

**Description**

In mod_auth_ldap bind mode, test_password did not reject an empty password
before consulting the LDAP directory. Some directory servers, including Active
Directory and possibly Samba AD/DC, accept an empty simple bind as an
unauthenticated bind. SASL PLAIN rejects empty passwords, but mod_legacyauth
passed empty values to test_password, as could other consumers such as HTTP
basic-auth modules.

The legacy authentication path now applies SASLprep and rejects empty or
invalid passwords after preparation.

**Affected configurations**

The issue affects deployments using mod_auth_ldap in bind mode together with
mod_legacyauth or another auth interface that accepts empty passwords.
mod_legacyauth is not enabled in the default configuration.

**Mitigation**

Operators who cannot upgrade immediately should ensure that mod_legacyauth is
disabled (it is disabled by default). If your directory accepts empty
passwords, this may not be a complete mitigation.

**Fixes**

mod_auth_ldap now fails empty passwords without consulting the directory.
mod_legacyauth applies SASLprep and rejects empty or invalid values.

Commits: 2d4daeea5063 (mod_auth_ldap), ed8ace2a78fd (mod_legacyauth)

**Attribution**

The issue was identified in an external security review.

MUC mediated invites and declines relay arbitrary message children
---------------

Prosody issues
: #2040

CVEs
: Request pending

CWEs
: CWE-441

Affected versions
: All 13.0 versions prior to 13.0.8

Fixed versions
: 13.0.8

**Description**

In the mediated invite and mediated decline flows described in XEP-0045, the
MUC is responsible for sending the invitation stanza and the decline stanza to
the invitee/inviter respectively.

In both cases Prosody relayed the full original stanza with some metadata
added. However, this caused the MUC to effectively act as a relay for fairly
arbitrary message stanzas, and in a public MUC access to mediated invites is
unrestricted. As mediated invites/declines originate from the MUC's own bare
JID, this could enable spoofing certain stanzas which could confuse receiving
clients.

**Affected configurations**

Prosody prior to 13.0.8 is affected, if a MUC component is enabled. It is
especially vulnerable to abuse if it hosts public channels.

**Mitigation**

The best mitigation is to upgrade to Prosody 13.0.8. Alternatively, only host
members-only channels for trusted users.

**Fixes**

Prosody now generates a clean stanza with only the necessary metadata in it,
it does not relay the original stanza from the sender of the invite/decline.

Memory Exhaustion via Aborted HTTP Requests
-------------------------------------------------------

Prosody issue
: #2020

CVEs
: Request pending

CWEs
: CWE-400, CWE-770

Affected versions
: All 13.0 versions prior to 13.0.8

Fixed versions
: 13.0.8

**Description**

A remote, unauthenticated attacker can cause Prosody to retain memory when
an HTTP connection carrying an incomplete response is closed. The affected
code path is used by BOSH long-polling, but the underlying HTTP server issue
applies to any handler that holds a response open.

When the client disconnects, the request's async runner remains referenced
from util.async's waiting_runners table. The request, response and connection
objects therefore remain reachable indefinitely. Repeated requests consume
memory without requiring authentication.

**Affected configurations**

All 13.0 deployments prior to 13.0.8 are believed to be affected. Exposure is
highest where mod_bosh is enabled and reachable by untrusted clients.
Deployments behind a reverse proxy may also experience the leak when the proxy
abandons upstream requests.

**Mitigation**

Operators who cannot upgrade immediately should limit request rates and
concurrent connections at the reverse proxy or firewall, and should configure
proxy timeouts so abandoned upstream requests are rare. Restarting Prosody
releases the retained memory but does not prevent recurrence.

**Fixes**

The HTTP server now completes and releases the waiting runner when a
connection is closed with an open response, marks the HTTP session as
disconnected, and does not resume destroyed connections or dispatch queued
requests after disconnect.

Commit: f215eb8ec541

**Attribution**

The issue was reported privately to the Prosody team by an operator.

mod_bosh and mod_component don't apply child element limit
----------------------------------------------------------

Prosody issues
: #2035

CVEs
: Request pending

CWEs
: CWE-770

Affected versions
: All 13.0 versions prior to 13.0.8

Fixed versions
: 13.0.8

**Description**

mod_bosh and mod_component did not initialize the stream with a max child
element limit. While components are generally more trusted, this allowed
clients to bypass the limits usually imposed on c2s streams by using mod_bosh
instead, and in some cases components may relay arbitrary data that could

**Affected configurations**

Deployments with mod_bosh enabled (not enabled by default) or external
components (none by default) are affected.

**Mitigation**

Upgrade to 13.0.8, otherwise disable mod_bosh. mod_bosh is used by web clients,
but mod_websocket is often a suitable alternative.
