Cpanel::JSON::XS versions before 4.80 for Perl leak the decoded key of
an object rejected for a duplicate key or a missing colon in decode_hv

Description
-----------
Cpanel::JSON::XS versions before 4.80 for Perl leak the decoded key of
an object rejected for a duplicate key or a missing colon in decode_hv.

A quoted key of 24 or more bytes, or one containing a non-ASCII byte or
an escape sequence, is decoded into a new scalar. Nothing frees that
scalar when the object is rejected for a missing ':' after the key or,
from 4.09, for a duplicate key. Duplicate keys are an error unless
allow_dupkeys, dupkeys_as_arrayref or relaxed is set.

A process that keeps running after a failed decode retains one key per
rejected document, with its size chosen by the sender. Repeated
requests exhaust process memory.

Problem types
-------------
- CWE-401 Missing Release of Memory after Effective Lifetime

Solutions
---------
Upgrade to Cpanel-JSON-XS 4.80 or later.

References
----------
https://github.com/rurban/Cpanel-JSON-XS/commit/532b53cf8d2ca5ab6bc24048325566d1f7132425.patch
https://metacpan.org/release/RURBAN/Cpanel-JSON-XS-4.80/changes

Cpanel::JSON::XS versions before 4.80 for Perl allow stack exhaustion
via nested tagged values under allow_tags in decode_tag

Description
-----------
Cpanel::JSON::XS versions before 4.80 for Perl allow stack exhaustion
via nested tagged values under allow_tags in decode_tag.

With allow_tags, "(" starts a tagged value. Its tag and value are
decoded recursively, and each can start another tagged value. Unlike
arrays and objects, this nesting is not counted against max_depth.

A run of "(" bytes exhausts the C stack and triggers an uncatchable
segmentation fault regardless of max_depth.

Problem types
-------------
- CWE-674 Uncontrolled Recursion

Solutions
---------
Upgrade to Cpanel-JSON-XS 4.80 or later.

Cpanel::JSON::XS versions from 4.33 before 4.80 for Perl miss duplicate
non-ASCII bare keys, allowing type confusion under dupkeys_as_arrayref
in decode_hv

Description
-----------
Cpanel::JSON::XS versions from 4.33 before 4.80 for Perl miss duplicate
non-ASCII bare keys, allowing type confusion under dupkeys_as_arrayref
in decode_hv.

With allow_barekey, which relaxed enables, a bare key containing a
non-ASCII byte is stored as UTF-8 but looked up as raw bytes, so a
repeated key escapes the duplicate-key check and replaces the earlier
value.

From 4.41, under dupkeys_as_arrayref, a bare repeat replaces the array
that collects a key's values with a plain value, and the next quoted
repeat pushes onto that value as if it were an array. A JSON integer
there is dereferenced as a pointer.

Untrusted JSON decoded with relaxed and dupkeys_as_arrayref can crash
the process or dereference an address chosen by a JSON number.

Problem types
-------------
- CWE-843 Access of Resource Using Incompatible Type ('Type Confusion')
- CWE-176 Improper Handling of Unicode Encoding

Solutions
---------
Upgrade to Cpanel-JSON-XS 4.80 or later.

References

-----------
Cpanel::JSON::XS versions from 4.33 before 4.80 for Perl accept

With utf8 and allow_barekey, which relaxed enables, a quoted key is
validated as UTF-8 but a bare key's bytes are stored as a UTF-8 flagged

again, die with a malformed UTF-8 error.

Cpanel::JSON::XS versions before 4.80 for Perl allow memory exhaustion
by encoding exponent notation as full decimal digits under allow_bignum

Description
-----------
Cpanel::JSON::XS versions before 4.80 for Perl allow memory exhaustion
by encoding exponent notation as full decimal digits under
allow_bignum.

With allow_bignum, a JSON number with a fraction or exponent decodes to
a Math::BigFloat, which stores the exponent separately and so decodes
cheaply. Encoding it untyped or as JSON_TYPE_FLOAT writes the plain
decimal form with one digit per unit of exponent. Nothing bounds the
exponent, so the 12-byte text [1e30000000] encodes to 30 MB.

Untrusted JSON decoded with allow_bignum and encoded again can exhaust
memory and CPU.

Problem types
-------------
- CWE-405 Asymmetric Resource Consumption (Amplification)

Solutions

Upgrade to Cpanel-JSON-XS 4.80 or later.

Cpanel::JSON::XS versions before 4.80 for Perl allow memory exhaustion
by buffering incremental input past max_size in incr_parse

Description
-----------
Cpanel::JSON::XS versions before 4.80 for Perl allow memory exhaustion
by buffering incremental input past max_size in incr_parse.

The parser appends each chunk to its buffer. In scalar or list context,
it compares max_size with how far it has progressed, not with the
buffer length. A chunk that starts with a NUL byte stops the parser
before it progresses, and a call in void context skips the check, so
the buffer grows without limit.

A peer streaming data to an incr_parse consumer can exhaust process
memory regardless of max_size.

Problem types
-------------
- CWE-770 Allocation of Resources Without Limits or Throttling

Solutions
---------
Upgrade to Cpanel-JSON-XS 4.80 or later.

Cpanel::JSON::XS versions from 4.20 before 4.80 for Perl write out of

encode_hv

Description
-----------
Cpanel::JSON::XS versions from 4.20 before 4.80 for Perl write out of
bounds when a tied or shared hash grows during canonical encoding in
encode_hv.

With canonical, the keys of a tied or threads::shared hash are counted
before a second pass collects them for sorting. The encoder uses a
fixed 64-entry stack array or, for larger counts, a heap array sized
from the first pass. If the second pass exceeds that capacity, entries
are written out of bounds before the counts are compared.

This corrupts stack or heap memory and can crash the process.

Problem types

Upgrade to Cpanel-JSON-XS 4.80 or later.

Cpanel::JSON::XS versions before 4.80 for Perl use the parent
interpreter's scalars from a parser object cloned into a new ithread

Description
-----------
Cpanel::JSON::XS versions before 4.80 for Perl use the parent
interpreter's scalars from a parser object cloned into a new ithread.

A parser object holds its callbacks and its incremental parse buffer as
raw scalar pointers. When a thread is created, these are copied into
the new interpreter unchanged, so the child's parser uses, and later
frees, scalars that belong to the parent and may already have been
freed there.

A parser created before a thread starts and used inside it can call
freed callbacks, corrupt reference counts and crash the process.

Problem types
-------------
- CWE-416 Use After Free

Solutions
---------
Upgrade to Cpanel-JSON-XS 4.80 or later.

-----------
Cpanel::JSON::XS versions from 4.42 before 4.80 for Perl let input

allow_nonref is enabled by default and incr_parse inherits it. A
top-level number, true, false or null has no closing delimiter, so the

one value when read together, but as 1 and then 2 when split across two
reads.

A peer that can influence read boundaries can change how many messages
a stream consumer decodes and what values they carry.

-----------
Cpanel::JSON::XS versions from 3.0202 before 4.80 for Perl leak memory

-----------
Cpanel::JSON::XS versions before 4.80 for Perl leak the decoded

Cpanel::JSON::XS versions from 4.43 before 4.80 for Perl misorder

characters. A byte-string key whose bytes are valid UTF-8 is sorted out
of order, and two keys that encode differently can compare equal and
are left in hash order.

The same data can encode to different canonical documents across
processes.

Description
-----------
Cpanel::JSON::XS versions from 4.51 before 4.80 for Perl allow
quadratic CPU use by revalidating the remaining buffer per value in
incr_parse.

At the first non-ASCII byte in a string, the decoder validates UTF-8
from there to the end of its input. incr_parse decodes each buffered
value with a fresh decoder, so every value revalidates the rest of the
buffer, and doubling the input quadruples the work.

A peer that sends about a megabyte of ordinary non-ASCII JSON in one
read ties up the process for seconds of CPU time.

Problem types

Upgrade to Cpanel-JSON-XS 4.80 or later.
