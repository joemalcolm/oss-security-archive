Subject: Apache bRPC security advisory: 35 vulnerabilities fixed in 1.18.0

Hi, all

We have released the Apache bRPC 1.18.0, with 35 vulnerabilities fixed
(16 high, 19 moderate) . The vulnerabilities descriptions are below:

### CVE-2026-48830: Apache bRPC: HTTP builtin request can mark a
connection authenticated and bypass auth for later requests

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

Improper authentication in Apache bRPC through 1.17.0 allows a remote
unauthenticated attacker to bypass authentication for protected
non-builtin HTTP endpoints by first sending a builtin HTTP request on
the same HTTP/1.1 keep-alive connection.

When ServerOptions.auth is enabled and builtin HTTP services are
exposed on the public listener, a builtin request received as the
first message on a socket may cause the connection to be treated as
authenticated for later requests on that socket. Users are recommended
to upgrade to version 1.18.0, which fixes this issue, or apply this PR
separately:  https://github.com/apache/brpc/pull/3308

### CVE-2026-54425: Apache bRPC: Stack Exhaustion via Recursive HPACK
Dynamic Table Size Update Decoding

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

Uncontrolled recursion in the HTTP/2 HPACK decoder in Apache bRPC
before 1.18.0 allows remote attackers to cause denial of service by
sending a crafted HTTP/2 header block containing many consecutive
Dynamic Table Size Update entries. Each update was decoded by
recursively invoking the HPACK decoder, which could exhaust the thread
stack before a header field or end of input was reached.

Root Cause:
The bRPC HPACK decoder recursively decoded the next entry after
processing a Dynamic Table Size Update. The decoder did not bound the
recursion depth, so a long sequence of update entries could consume
excessive stack space.

Affected Scenarios:
Use bRPC with the built-in HTTP/2 implementation to accept HTTP/2
traffic from an untrusted network.

How to Fix:
1. Upgrade bRPC to version 1.18.0, which fixes this issue.
2. Apply this patch:  https://github.com/apache/brpc/pull/3343

Note:
The fix changes HPACK Dynamic Table Size Update decoding to use
iterative parsing instead of recursive parsing.

Credit:

黄宏洋(Huang Hongyang) (finder)

References:

https://github.com/apache/brpc
https://www.cve.org/CVERecord?id=CVE-2026-54425

### CVE-2026-54426: Apache bRPC: Stack Exhaustion via Unbounded
Recursion in Redis Reply Parser

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

Uncontrolled recursion in the Redis reply parser in Apache bRPC <
1.18.0 allows a remote Redis server peer to crash a bRPC Redis client
process by returning a deeply nested RESP array reply. The parser
recursed once for each nested array level without enforcing a depth
limit. The fix adds a configurable Redis reply depth limit with
default value 128 and rejects replies exceeding that limit.

Affected Scenarios:
Applications using bRPC as a Redis client with
ChannelOptions.protocol="redis" and receiving replies from an
untrusted or faulty Redis server peer.

How to Fix:
1. Upgrade Apache bRPC to 1.18.0.
2. Apply the patch from PR  https://github.com/apache/brpc/pull/3344 .

Note:
After applying the fix, Redis replies with array nesting deeper than
redis_max_reply_depth are rejected.

Credit:

Nikko Enggaliano Pratama (nikkoenggaliano@...il.com) on Github (finder)

https://github.com/apache/brpc
https://www.cve.org/CVERecord?id=CVE-2026-54426

### CVE-2026-54427: Apache bRPC: Stack Exhaustion via Unbounded
Recursion in AMF Parser

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

Uncontrolled recursion in the AMF parser in Apache bRPC < 1.18.0
allows a remote RTMP peer to crash a bRPC process by sending deeply
nested AMF objects or arrays. The parser recursively processed nested
AMF containers without enforcing a depth limit, which could exhaust
the native stack.

Affected Scenarios:
Applications using bRPC RTMP support and parsing AMF data from an
untrusted RTMP peer. This includes RTMP servers parsing client command
messages, RTMP clients parsing server responses or status messages,
and either side parsing inbound AMF script data such as metadata or
cue points. Direct callers of ReadAMFObject or ReadAMFArray on
untrusted input are also affected.

How to Fix:
1. Upgrade Apache bRPC to 1.18.0.
2. Apply the patch from PR  https://github.com/apache/brpc/pull/3344 .

Note:
The fix introduces a configurable AMF nesting depth limit with default
value 128. AMF objects or arrays deeper than amf_max_depth are
rejected after applying the fix.

https://github.com/apache/brpc
https://www.cve.org/CVERecord?id=CVE-2026-54427

### CVE-2026-56386: Apache bRPC: Integer Underflow and Out-of-Bounds
Read in HTTP/2 DATA Frame Parser

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

Integer underflow and out-of-bounds read in the HTTP/2 server DATA
frame parser in Apache bRPC allows an unauthenticated remote attacker
to cause denial of service by sending a malformed DATA frame with the
PADDED flag set and a zero-length payload.

Root Cause:
The HTTP/2 DATA frame handler computed the fragment size from the
attacker-controlled payload length and, when the PADDED flag was
present, decremented the fragment size before ensuring that the frame
contained the mandatory pad length byte. A zero-length padded DATA
frame could therefore underflow the unsigned fragment size and read
the pad length byte past the end of the frame buffer.

Affected Scenarios:
Apache bRPC servers that accept HTTP/2 traffic are affected when a
remote client can send crafted HTTP/2 frames to the server. HTTP/2 may
be reached through cleartext h2c detection on an HTTP port or through
TLS ALPN negotiation.

How to Fix:
(Choose one of the following options)
1. Upgrade Apache bRPC to version 1.18.0, which fixes this issue.
2. Apply this patch:  https://github.com/apache/brpc/pull/3325

Note:
The fix validates that a padded DATA frame has enough payload bytes
for the pad length field before decrementing the fragment size or
reading the pad length byte. Malformed zero-length padded DATA frames
are rejected with HTTP/2 FRAME_SIZE_ERROR.

Credit:

Nikko Enggaliano Pratama (finder)

References:

https://github.com/apache/brpc
https://www.cve.org/CVERecord?id=CVE-2026-56386

### CVE-2026-56387: Apache bRPC: Remote Memory Exhaustion in RTMP AMF Parser

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

The RTMP AMF parser in Apache bRPC accepts AMF string lengths and
array counts directly from untrusted input. A remote unauthenticated
attacker who can reach a bRPC server with RTMP enabled can send a
small AMF payload with an excessive declared long string length or
array count, causing excessive memory allocation or resource
consumption before the parser rejects the incomplete payload.

Root Cause:
The AMF long string parser resized the destination string to the
declared 32-bit length before validating that the stream contained
that many bytes. ECMA array and strict array parsers also accepted
32-bit element counts without a configurable upper bound.

Affected Scenarios:
Deployments that enable the bRPC RTMP server component and accept RTMP
traffic from untrusted clients. Direct uses of the AMF parser on
untrusted data are also affected.

How to Fix:
1. Upgrade bRPC to version 1.18.0, which fixes this issue.
2. Apply this patch:  https://github.com/apache/brpc/pull/3353

Note:
The fix introduces configurable AMF parsing limits. The default
maximum string size is 64 MiB and the default maximum array element
count is 1,048,576. Payloads above these limits are rejected. The
limits can be adjusted with amf_max_string_size and
amf_max_array_size.

### CVE-2026-56388: Apache bRPC: Out-of-Bounds Write in Redis Command Parser

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

The Redis server command parser in Apache bRPC accepts an empty RESP
array as a command header. A remote unauthenticated attacker who can
reach a bRPC server with Redis service enabled can send an empty array
header followed by a bulk string, causing an out-of-bounds write in
the parser and crashing the process.

Root Cause:
RedisCommandParser::ConsumeImpl rejected negative RESP array counts
but accepted zero. It resized the command argument vector to zero
elements and continued parsing. When a following bulk string was
parsed, the only index guard was a CHECK. In configurations where
fatal logs do not abort immediately, execution could continue and
write to _args[0] even though the vector was empty.

Affected Scenarios:
Deployments that enable ServerOptions.redis_service and accept Redis
protocol traffic from untrusted clients. The issue is reached during
parsing before command handling or authentication.

How to Fix:
1. Upgrade bRPC to version 1.18.0, which fixes this issue.
2. Apply this patch:  https://github.com/apache/brpc/pull/3354

Note:
The fix rejects empty RESP arrays as invalid Redis commands and
replaces the internal index CHECK with an explicit parse error so
malformed command streams cannot fall through to an indexed vector
write.

Credit:

Nikko Enggaliano Pratama (finder)

References:

https://github.com/apache/brpc
https://www.cve.org/CVERecord?id=CVE-2026-56388

### CVE-2026-58064: Apache bRPC: Denial of Service via Unbounded Redis
Inline Command Allocation

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

The Redis protocol implementation in Apache bRPC allowed inline
command parsing to allocate and copy the full connection buffer before
a complete CRLF-terminated command was available. A remote attacker
with access to a Redis-protocol bRPC service could send long inline
inputs without a terminating CRLF to increase memory usage and CPU
copy overhead, potentially causing denial of service.


Root Cause:
The Redis inline command parser allocated memory based on the current
input buffer size and copied the entire buffer before determining the
current inline command boundary. The existing
redis_max_allocation_size limit was applied to RESP bulk strings and
arrays, but not effectively to the inline command path before
allocation.


Affected Scenarios:
Use Apache bRPC server with Redis protocol enabled and reachable by
untrusted clients.


How to Fix:
1. Upgrade Apache bRPC to version 1.18.0, which fixes this issue.
2. Apply the patch from PR  https://github.com/apache/brpc/pull/3363 .


Note:
The fix applies redis_max_allocation_size to Redis inline command
lines and scans for CRLF before allocating parser arena memory. Inline
command lines exceeding this limit are rejected.

Credit:

73Lab of Qingteng.cn (finder)

### CVE-2026-61902: Apache bRPC: Memory Exhaustion Through
Inconsistent Message Body Limits

Severity: medium

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

Apache bRPC versions before 1.18.0 do not consistently enforce the
configured max_body_size limit in non-progressive HTTP/1 and HTTP/2
parsing and in memcache and couchbase response parsing.

A remote unauthenticated peer can cause an affected process to buffer
message data beyond the configured limit, which may lead to memory
exhaustion and denial of service.

https://github.com/apache/brpc/pull/3382 . The fix rejects oversized

### CVE-2026-61916: Apache bRPC: Out-of-bounds Read in URL and Header
Lookup Tables on Unsigned-char Platforms

Severity: moderate

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

Out-of-bounds reads in URL parsing and case-insensitive header lookup
in Apache bRPC before version 1.18.0 on platforms where plain char is
unsigned, such as ARM64, allow remote attackers to cause a process
crash and denial of service by sending crafted input containing bytes
with the high bit set.

Root Cause:
Two 256-entry lookup tables are accessed through pointers biased by
128 so that valid indices are in the range -128 to 127. Input bytes
are promoted from plain char to int without first normalizing them to
the signed-char range. On affected platforms, bytes in the range 0x80
to 0xFF therefore become indices 128 to 255 and read up to 127 bytes
beyond the end of the underlying tables.

Affected Scenarios:
A remotely accessible bRPC HTTP server on an affected platform can
reach the vulnerable URL lookup through an unauthenticated request URI
containing a high-bit byte. The case-insensitive lookup is also
reachable when untrusted header names are processed through APIs such
as the HTTP/2 HPACK path. HTTP/1 header names containing high-bit
bytes are rejected by the HTTP/1 parser before reaching the vulnerable
lookup. Builds where plain char is signed, which commonly include
x86_64 builds, are not affected by this issue.

How to Fix:
Choose one of the following options:
1. Upgrade Apache bRPC to version 1.18.0 or later.
2. Apply the patch from  https://github.com/apache/brpc/pull/3376 .

The fix normalizes lookup-table indices to the signed-char range
before accessing the biased tables.

Credit:

Ubeddulla Khan (finder)

References:

https://github.com/apache/brpc
https://www.cve.org/CVERecord?id=CVE-2026-61916

### CVE-2026-66392: Apache bRPC: TLS Client Accepts Certificates for
Mismatched Peer Names

Severity: medium

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

Apache bRPC versions before 1.18.0 validate the server certificate
chain when client TLS peer verification is enabled, but do not bind
the certificate to an expected DNS name or IP address. A network
attacker who can redirect or intercept a connection and who possesses
a certificate issued by a CA trusted by the client for another name
may impersonate the requested TLS endpoint.


Affected Scenarios:
Applications use a bRPC client Channel to connect to an untrusted
network with certificate verification enabled and trust a CA that can

verify_depth. HTTPS Channels automatically verify the certificate

identity differs from the URL host. Alternatively, apply the patch
from  https://github.com/apache/brpc/pull/3408 .

The new option performs DNS SAN or IP SAN verification during the TLS
handshake. Configurations that set expected_peer_name while peer
verification is disabled are rejected.

### CVE-2026-74755: Apache bRPC: Integer Underflow in mcpack2pb Parser
Leading to Denial of Service

Severity: moderate

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

An integer underflow in the mcpack2pb component of Apache bRPC
(version < 1.18.0) on all platforms allows remote attackers to crash a
bRPC server by sending a request containing a string field with a zero
value_size. The UnparsedValue::as_string() function computes `_size -
1` without validating `_size`; when value_size is 0 the expression
underflows to SIZE_MAX, resize() throws std::length_error, and because
the exception is not caught on the request parsing path the process
aborts (SIGABRT).

Root Cause:
In src/mcpack2pb/parser.cpp, UnparsedValue::as_string() resizes the
output string to `_size - 1`, where `_size` is the value_size of a
string field taken directly from the network data. A value_size of 0
underflows the unsigned size_t, and the subsequent resize() throws an
exception that is not caught.

Affected Scenarios:
bRPC servers that accept nshead frames wired to the ubrpc mcpack2
adaptor (for example the NsheadService + UbrpcMcpack2Adaptor
deployment pattern) can be crashed by a single unauthenticated
request. Stock open-source bRPC registers the ubrpc/nshead_mcpack
protocols as client-only, so default server configurations are not
affected.

How to Fix:
1. Upgrade bRPC to a version that includes this fix.
2. Apply the patch in PR  https://github.com/apache/brpc/pull/3450

Credit:

Feng Zhijie (Independent security researcher) (finder)

### CVE-2026-74757: Apache bRPC: Uncontrolled Memory Allocation via
Malicious mcpack Array Item Count

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

Uncontrolled resource allocation in the mcpack2pb component in Apache
bRPC (version < 1.18.0) on all platforms allows remote attackers to
make the server allocate a large amount of memory via sending a
crafted mcpack request with a huge array item count.

The bRPC mcpack2pb parser trusts the item count stored in the mcpack

Use a bRPC server that wires a NsheadService to UbrpcMcpack2Adaptor
(the Baidu ubrpc deployment pattern) and parses requests with code
generated by the mcpack2pb protoc plugin. The request body is parsed
before authentication.

How to Fix:
(Choose one of the following options)
1. Upgrade bRPC to version 1.18.0, which fixes this issue.
2. Apply this patch:  https://github.com/apache/brpc/pull/3451

Note:
No matter which option you choose, you should know that the fix caps
the array item count to the remaining bytes of the array payload.

Feng Zhijie (Dopamine) (finder)

### CVE-2026-74758: Apache bRPC: Heap Use-After-Free in RTMP Abort
Message Handling

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

A heap use-after-free in the RTMP protocol component of Apache bRPC
(versions < 1.18.0) allows a remote attacker to crash a bRPC RTMP
server by sending a crafted Abort control message. No authentication
or application-level request is required.

Root Cause:
When an RTMP Abort control message names the chunk stream that is
currently being parsed (the chunk stream carrying the message itself),
RtmpChunkStream::OnAbortMessage calls RtmpContext::ClearChunkStream,
which deletes the RtmpChunkStream while its Feed() is still running.
After the message handler returns, Feed() continues to access members
of the deleted object, resulting in a heap-use-after-free.

Affected Scenarios:
bRPC servers that enable RTMP support (ServerOptions.rtmp_service set)
and accept connections from untrusted networks.

How to Fix:
1. Upgrade bRPC to version 1.18.0, which fixes this issue.
2. Apply this patch:  https://github.com/apache/brpc/pull/3452

The fix skips clearing the chunk stream when the Abort message targets
the chunk stream that is currently being parsed.

### CVE-2026-78048: Apache bRPC: Remote Denial of Service via
Out-of-Bounds Dynamic Table Sizing in HPACK Decoder

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

A reachable-assertion flaw in the HPACK header-compression decoder of
the HTTP/2 (h2/gRPC) stack in Apache bRPC (version < 1.18.0) on all
platforms allows a remote attacker to crash the server process by
sending a crafted sequence of HPACK headers, resulting in a denial of
service.

Root Cause:
In src/brpc/details/hpack.cpp, IndexTable::Init sizes the
dynamic-table ring buffer as num_headers = max_size / (32 + 2), i.e.
it assumes a minimum table entry of 34 bytes (name >= 1 byte + value
>= 1 byte + 32 bytes of overhead). However, RFC 7541 section 4.1
specifies that the minimum entry size is 33 bytes, because the value
may be empty (name >= 1 byte + value == 0 + 32 bytes). For the default
4096-byte table this allocates only 120 slots (4096/34). Eviction in
AddHeader is driven by byte usage (_max_size), not by slot count, so a
peer can add 121 minimal 33-byte entries (121*33 = 3993 <= 4096)
without triggering eviction. The 121st AddHeader then hits
CHECK(!_header_queue.full()), which aborts the process.

Affected Scenarios:
Use a bRPC server that serves HTTP/2 or gRPC requests (e.g. via the h2
protocol) from an untrusted network. The malicious header block is
processed during HPACK decoding of incoming requests without
authentication.

How to Fix:
(Choose one of the following options)
1. Upgrade bRPC to version 1.18.0, which fixes this issue.
2. Apply this patch: https://github.com/apache/brpc/pull/3462

Note:
The fix sizes the dynamic table for the 33-byte minimum entry
(max_size / (32 + 1)) and ensures at least one ring-buffer slot is
kept when max_size is smaller than the minimum entry, so that
initialization cannot fail on malloc(0).

Credit:

ubeddulla khan (finder)

References:

https://github.com/apache/brpc
https://www.cve.org/CVERecord?id=CVE-2026-78048

### CVE-2026-78058: Apache bRPC: Unbounded Resource Consumption and
Crash in the HTTP/2 Receive Path

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

Uncontrolled resource consumption in the HTTP/2 (h2) receive path of
Apache bRPC (version < 1.18.0) on all platforms allows a remote
unauthenticated attacker to crash the server or grow its memory
without bound by sending crafted HTTP/2 frames.

Root Cause:
The h2 parser, enabled by default on every bRPC server port and used
by h2/gRPC clients, trusts the peer to respect receive-side limits
that bRPC advertises but never enforces:
1. SETTINGS_MAX_CONCURRENT_STREAMS defaulted to unlimited and was
never checked on the server, letting a peer pin an unbounded number of
pending streams per connection (~100x memory amplification).
2. SETTINGS_MAX_HEADER_LIST_SIZE defaulted to unlimited and was never
enforced; 1-byte HPACK indexed references amplify a small HEADERS
frame ~4000x into an unbounded decoded header list ("HPACK bomb"), and
a never-completed HEADERS/CONTINUATION block accumulates memory
without limit.
3. Control-frame acks (PING/SETTINGS acks, RST_STREAM, GOAWAY,
WINDOW_UPDATE) unconditionally bypassed the
-socket_max_unwritten_bytes write cap, so a PING flood combined with
withheld TCP reads grew the connection buffer without the documented
bound.
4. The HPACK dynamic table size update was validated against the
protocol default (4096) instead of the advertised
SETTINGS_HEADER_TABLE_SIZE, which together with the dynamic-table
queue/accounting issue can desynchronize the decoder and dereference
NULL (crash).

Affected scenarios:
Any bRPC server serving HTTP/h2/gRPC to an untrusted network, and any
bRPC h2/gRPC client connecting to an untrusted backend. The h2 parser
runs before any Authenticator check on the shared port.

How to fix:
Upgrade bRPC, or apply the patch in https://github.com/apache/brpc/pull/3474.

Note:
After applying the fix the following limits are enforced by default:
- max_concurrent_streams: 1024 per connection (4294967295 restores unlimited).
- max_header_list_size: 1 MiB decoded size per stream (4294967295
restores unlimited; -h2_client_max_header_list_size for clients).
- h2 control-frame acks respect -socket_max_unwritten_bytes
(-h2_ack_ignore_eovercrowded restores the old behavior).
Requests exceeding these limits are rejected
(RST_STREAM(REFUSED_STREAM) or a connection error).

Credit:

Claude (finder)

References:

https://github.com/apache/brpc
https://www.cve.org/CVERecord?id=CVE-2026-78058

### CVE-2026-78066: Apache bRPC: Resource Exhaustion via Unbounded
Decompression and Unvalidated Wire-Declared Sizes

Severity: high

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

http_allow_obs_fold=true restores acceptance of folded
Content-Length/Transfer-Encoding values, and
http_strict_header_token=true additionally rejects spaces inside any
header field name (not only the ones that decide framing). Legitimate
clients that do not use these obsolete forms are unaffected.

### CVE-2026-86147: Apache bRPC: Arbitrary file creation/truncation
via /flags and unbounded profiling duration via /pprof

Severity: moderate

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

External control of file name or path and uncontrolled resource
consumption in Apache bRPC (version < 1.18.0) on all platforms allows
remote attackers who can reach the builtin service port to create
directories and truncate/overwrite files with the privileges of the
server process, or to hold the process-wide CPU/contention profiler
for an arbitrarily long time.

Root Cause:
1. The builtin /flags service allows gflags carrying a validator to be
modified at runtime via ?setvalue=. The bvar/mbvar dump path gflags
(bvar_dump_file, bvar_dump_tabs, mbvar_dump_file) were registered with
an accept-anything validator whose only purpose was to wake the
dumping thread. A remote attacker could therefore repoint the dump
path (e.g. GET /flags/bvar_dump_file?setvalue=/victim/dir/target
followed by GET /flags/bvar_dump?setvalue=true, or the equivalent for
mbvar_dump_file, which is used verbatim without a forced suffix),
making the dumping thread recursively create directories and
open/truncate files at attacker-chosen locations. Tab names in
bvar_dump_tabs were appended to the path without sanitization,
allowing '..' to escape the configured directory.
2. The /pprof builtin service did not clamp the ?seconds= parameter to
FLAGS_max_profiling_seconds (a limit that /hotspots enforced). A
single request such as ?seconds=2147483647 made the handler sleep for
decades while holding the process-wide gperftools CPU profiler or
bthread contention profiler, so /hotspots/cpu and /hotspots/contention
returned 503 for everyone else during that time.

Affected Scenarios:
Any Apache bRPC server exposing the builtin services (enabled by
default on the same port as normal RPC traffic) to untrusted networks.

How to Fix:
(Choose one of the following options)
1. Upgrade bRPC to version 1.18.0, which fixes this issue.
2. Apply this patch:  https://github.com/apache/brpc/pull/3523

Note:
After the fix, bvar_dump_file, bvar_dump_tabs and mbvar_dump_file can
no longer be modified at runtime through the /flags builtin service.
They can still be changed programmatically via
google::SetCommandLineOption(), taking effect on the next dump cycle.
The profiling duration of /pprof is now capped by the
-max_profiling_seconds gflag (default 300 seconds), which can be
adjusted by the server owner.

### CVE-2026-86249: Apache bRPC: Authentication bypass when a server
sets ServerOptions.internal_port and ServerOptions.auth

Severity: moderate

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

On a brpc::Server that sets both ServerOptions.auth and
ServerOptions.internal_port, the HTTP built-in service exemption on
internal_port can be abused to bypass authentication entirely.
VerifyHttpRequest() returns true without checking any credential when
a built-in service is requested on internal_port, and this verdict is
not per - request: verification runs only for the first message of a
connection and the result latches the connection. Sending a request
such as GET /status to internal_port first authenticates the whole
connection, after which every subsequent request dispatched on the
same connection is handled without ever calling VerifyHttpRequest().
This lets a remote attacker reach ordinary (non-built-in, non-tabbed)
authenticated services without supplying valid credentials whenever
the server uses ServerOptions.internal_port together with an
Authenticator. The fix restricts internal_port so that it carries only
built-in and Tabbed services; requests for ordinary services sent to
internal_port are rejected with EPREM / HTTP 403.



Mitigation / Fix: upgrade to 1.18.0 or apply PR
https://github.com/apache/brpc/pull/3525 .



Users who rely on serving normal services on internal_port must move
those requests to the port passed to Server::Start().

### CVE-2026-87849: Apache bRPC: Out-of-bounds read via non-object
fields in Discovery naming-service reply parsing

Severity: moderate

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

The Discovery naming-service reply parser in Apache bRPC (versions <
1.18.0) calls RapidJSON object-only accessors (FindMember) on JSON
values without first validating that those values are objects. A
malformed Discovery response whose data/service members or instances
list contain non-object entries (e.g. a bare integer) triggers the
RapidJSON object-access precondition on the client, reading memory out
of bounds and potentially crashing the bRPC client.

Root Cause:
In src/brpc/policy/discovery_naming_service.cpp,
DiscoveryNamingService::GetServers() and
DiscoveryNames::ListDiscoveryNodes() access JSON values with member
functions on non-object values. RapidJSON only defines these
operations for object types; invoking them on a non-object violates
the class invariant and results in undefined behavior (out-of-bounds
read), commonly crashing the process.

Affected Scenarios:
An operator-configured (or compromised) Discovery backend returns a
malformed /discovery/nodes or /discovery/fetchs response whose
data/service/instance entries are not JSON objects, crashing any bRPC
client that refreshes its server list.

How to Fix:
1. Upgrade bRPC to version 1.18.0 or later, which fixes this issue.
2. Apply this patch: https://github.com/apache/brpc/pull/3533

The fix validates that the Discovery response data, per-service data,
and instance entries are JSON objects (and skips non-object
node/instance entries and rejects non-object data/service values)
before calling member accessors.

### CVE-2026-90484: Apache bRPC: Null pointer dereference in MySQL
reply parser leading to client crash

Severity: moderate

Affected versions:

- Apache bRPC (brpc) through 1.17.0
- Apache bRPC (brpc) 1.18.0 unaffected

Description:

The MySQL client response parser in Apache bRPC dereferences a null
pointer when the server peer sends a zero-payload-length response
packet. A response packet whose declared payload length is zero is
accepted by the frame-length check (is_full_package), after which the
parser reads the response type byte via an unbounded 5-byte fetch that
returns nullptr, and type = p[4] dereferences it, crashing the client
process.



Root Cause: In brpc::policy::MysqlReply::ConsumePartialIOBuf,
buf.fetch(header, 5) returns nullptr when the buffered data only holds
the 4-byte header of a zero-length packet, then the code reads p[4]
(and, in the fast-auth path, p2[4]) without checking for a null or
zero-length packet.



Affected Scenarios: A brpc MySQL client connecting to a malicious or
compromised MySQL server (or a MITM) can be crashed by a zero-length
server response packet, resulting in denial of service of the client.



Fix: The fix rejects zero-length response packets (returning
PARSE_ERROR_ABSOLUTELY_WRONG) both for the initial response type
determination and after a fast-auth marker, before reading the type
byte. Upgrade to the Apache bRPC version 1.18.0 or apply the PR patch
at https://github.com/apache/brpc/pull/3536.
